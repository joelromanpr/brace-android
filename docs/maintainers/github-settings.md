# GitHub repository settings checklist

These controls live in GitHub settings and cannot be established by files alone. Enable them after the first CI run creates the actual check names. The local `gh` credential was invalid during initial setup, so no hosted setting is claimed as configured.

1. **Settings → General → Features:** enable Discussions. Enable squash merge; disable merge commits and rebase merges if the team wants one consistent history. Enable automatic deletion of merged topic branches.
2. **Settings → Rules → Rulesets:** target the default `main` branch. Require a pull request and both `verify` and `instrumented` CI status checks after their first hosted runs have appeared. Block force pushes and branch deletion. Set required approving reviews to **zero** while there is only one maintainer; requiring self-approval would block release work. Do not require CODEOWNERS approval for a solo maintainer. Keep administrators subject to the rules unless a documented recovery need arises. Create a separate `v*` tag ruleset that blocks updates and deletion of release tags; the release workflow verifies their signatures.
3. **Settings → Pages:** choose **GitHub Actions** as the build and deployment source ([GitHub Pages setup](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)). The `docs-pages` workflow builds the site from the generated coverage JSON and deploys on `main`. Restrict the `github-pages` environment to `main`.
4. **Settings → Security:** enable private vulnerability reporting, Dependabot alerts and security updates, and code scanning if the plan allows. Confirm `SECURITY.md` points to a usable private reporting path.
5. **Settings → Environments:** create `maven-central`, limit workflow runs to `main`, and require a maintainer approval before the release workflow accesses publishing credentials. Leave “prevent self-review” off while there is only one maintainer, or the manual release will deadlock. The manual dispatch runs from `main` and verifies its tag input before staging. Add environment secrets `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`, `SIGNING_IN_MEMORY_KEY`, and `SIGNING_IN_MEMORY_KEY_PASSWORD` only here. Set the environment secret `MAVEN_CENTRAL_ENVIRONMENT_READY` to `configured` only after the approval rule is active; the release workflow fails closed without it. Never expose them to pull requests.
6. **Issues → Labels:** add at least `bug`, `question`, `dependencies`, `component`, `accessibility`, `good first issue`, `documentation`, `tokens`, `needs design`, `experimental`, and milestone labels `M0` through `M5`. Existing labels can remain.
7. **Projects:** create a public project board with fields for inventory ID, milestone, status, and priority. Link component issues to their inventory rows. The board is a work view; the inventory remains the coverage authority.

After enabling each setting, verify it in the repository UI. A local workflow file does not prove a hosted check has passed, Pages has published, or Maven Central is configured.
